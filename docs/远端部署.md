# 远端服务部署（v2.0.0）

此文档用于之后由管理员手动部署。当前没有连接远端服务器，没有迁移本机微信绑定，也没有修改本机正在运行的转发服务。代码通过本地自动化测试不等于已经在日本服务器验证过 Mercari 直连。

## 架构与边界

服务器常驻运行 Node.js 服务：HTTP 采集、关键词与屏蔽词配置、调度、上一轮商品码、微信账户及待发队列都保存在服务器。插件通过带管理员密钥的 HTTPS 接口控制开始、暂停和配置；插件关闭、本机关机不影响服务器运行。服务器采集不启动浏览器。

暂停一个关键词会停止该关键词的新采集请求并取消正在采集的请求。暂停全部监控不再访问 Mercari，管理 API 和微信会话维护仍运行；此前的微信待发队列与采集暂停分开处理。

微信仍受官方账号、登录及会话限制。扫码绑定后，接收人应在手机 ClawBot 聊天窗口发一条消息建立发送上下文。微信接口接受不代表手机一定显示；过期登录需要重新扫码，会话受限需要接收人回复。日本 IP 也不保证 Mercari 永不限制访问。遇到验证码、403、429 等应查看状态、暂停或降低访问频率，不绕过验证。

## 运行条件

- Linux 服务器示例采用 systemd、Caddy、Git、Node.js 和 npm。无需 Chrome、Playwright、桌面或图形界面。
- 使用 Node.js **24.22.0** 可与当前本机验证环境一致。固定 OpenClaw `2026.10.4` 的声明要求为 `>=24.16.0 <25 || >=26.1.0`；部署模板限定 Node 24。不要使用 Node 22 安装该固定组合。
- 腾讯官方插件固定为 `@tencent-weixin/openclaw-weixin@2.4.10`，启动时检查此版本。该插件自身声明 Node `>=22.13.0`、OpenClaw `>=2026.5.12`，但本项目运行条件以所固定 OpenClaw 的更高要求为准。
- 服务器需要可访问 Mercari 和微信官方 API；本机需可访问服务器 HTTPS 管理域名。不能仅凭地域确定网络可用。
- 使用私有仓库时，请在服务器单独配置只读部署密钥或自己的 GitHub 登录，不复制本机 Git 凭证，不将凭证写入远程 URL。

上游依据：[腾讯官方源码及协议](https://github.com/Tencent/openclaw-weixin)、[腾讯扫码流程源码](https://github.com/Tencent/openclaw-weixin/blob/main/src/auth/login-qr.ts)。本项目扫码管理器使用所固定版本导出的官方 HTTP 与账户存储帮助函数，适配手机数字配对码；不会启动需要 stdin 的 CLI 登录流程。上游将来升级可能改变这些接口，需要先测试再修改固定版本。

## 目录安排

建议将代码、依赖和私密数据分开：

```text
/opt/mercari-watch/current/             代码工作目录（Git 仓库）
/opt/mercari-runtime/                   固定版本的官方微信依赖
/var/lib/mercari-watch/                 持久数据，仅 mercari 用户可读写
  admin-token                          管理员密钥，首次启动生成，权限 600
  weixin/                              官方微信账户、会话、同步游标
  bridge/                              接收人、待发队列、删除记录
  ...                                  监控配置和采集状态
/etc/mercari-watch.env                  环境配置，权限 600
```

`MERCARI_DATA_DIR` 必须是仓库外的绝对路径。数据文件不进入 Git；更新代码不能覆盖数据目录。不要将凭证文件、真实 `.env`、接收人注册表或待发队列上传仓库。

## 安装示例

以下是供管理员逐条检查执行的 Linux 示例，按实际 Node 安装位置、域名和服务器用户调整。不要在已有同名目录上直接覆盖其他项目。首先确认 `node --version` 为合适的 Node 24 版本。

```sh
sudo useradd --system --create-home --home-dir /var/lib/mercari-watch --shell /usr/sbin/nologin mercari
sudo install -d -m 755 /opt/mercari-watch /opt/mercari-runtime
sudo install -d -m 700 -o mercari -g mercari /var/lib/mercari-watch
```

用管理员已授权的 Git 凭证将仓库克隆到 `/opt/mercari-watch/current`，然后：

```sh
cd /opt/mercari-watch/current
node --test tests/*.test.mjs
sudo cp deploy/runtime.package.json /opt/mercari-runtime/package.json
cd /opt/mercari-runtime
sudo npm install --omit=dev
```

安装官方依赖会下载 OpenClaw 及其依赖，可能需要时间和系统编译依赖。这里使用固定顶层版本；第一次安装后应保留生成的 `package-lock.json`，之后在相同运行环境用 `npm ci --omit=dev` 复现依赖。更新代码不要求每次重新安装官方依赖。不要在服务启动时自动执行 `npm install` 或升级到 `latest`。

在启动正式监控前，分别验证运行环境和日本服务器的 Mercari 直连：

```sh
cd /opt/mercari-watch/current
MERCARI_PLUGIN_ROOT=/opt/mercari-runtime/node_modules/@tencent-weixin/openclaw-weixin node tools/check-remote-install.mjs
node tools/probe-mercari-http.mjs --keyword '潔世一' --count 5
```

第一条在独立临时目录启动空服务，验证官方 SDK、无绑定启动和管理员接口，不访问 Mercari、不扫码或发送微信；第二条执行一次匿名 HTTP 搜索，只打印验证后的商品 ID，不写基线或发送通知。第二条必须在实际服务器返回 `ok: true` 才开始监控；失败时保持暂停，先查看网络、访问限制或协议变化。它不使用浏览器，也不会绕过验证码。不要为追求成功反复运行探测。

复制配置并编辑真实值：

```sh
sudo cp /opt/mercari-watch/current/deploy/remote.env.example /etc/mercari-watch.env
sudo chmod 600 /etc/mercari-watch.env
sudoedit /etc/mercari-watch.env
```

设置 `MERCARI_PUBLIC_URL=https://你的域名`、`MERCARI_TRUST_PROXY=1`，并将 `MERCARI_ALLOWED_ORIGINS` 设置为实际插件 ID 对应的 `chrome-extension://...`。生产 HTTPS 模式下，未在允许来源中登记的插件请求会被拒绝；如重新安装导致插件 ID 改变，需要更新允许来源并重启。不要填写 `*`。来源限制不代替管理员密钥，每次管理请求仍须验证密钥。服务始终绑定回环地址，避免将明文管理员接口直接暴露到公网。

检查 Node 真实可执行路径 `command -v node`。如果不是 `/usr/bin/node`，修改 `deploy/mercari-watch.service` 的 `ExecStart`，然后安装服务：

```sh
sudo cp /opt/mercari-watch/current/deploy/mercari-watch.service /etc/systemd/system/mercari-watch.service
sudo systemctl daemon-reload
sudo systemctl enable --now mercari-watch
sudo systemctl status mercari-watch --no-pager
sudo journalctl -u mercari-watch -n 50 --no-pager
```

配置域名 DNS 指向服务器，按 [Caddy 官方安装说明](https://caddyserver.com/docs/install)安装 Caddy。将 `deploy/Caddyfile` 中示例域名替换为实际域名并合并到服务器自己的 Caddy 配置，然后验证并重载。不要直接覆盖服务器已有站点。示例代理只开放 `/health` 和 `/api/*`，HTTPS 证书由 Caddy [自动管理](https://caddyserver.com/docs/automatic-https)。[反向代理配置](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)仅连接回环 Node 端口，服务只信任来自回环反向代理的 `X-Forwarded-Proto: https`。

初次启动时若没有在环境中设置 `MERCARI_ADMIN_TOKEN`，服务会创建 `/var/lib/mercari-watch/admin-token`。管理员通过可信 SSH 会话读取该文件并填入插件的远端连接配置。这个密钥等同于管理权限，请勿贴到聊天、截图或公开日志中。服务启动日志不会打印它。

## 插件连接与添加接收人

1. 重新加载项目的新版插件，切换到远端服务模式，填写 HTTPS 域名根地址和管理员密钥。
2. 点击连接，确认服务状态正常。先完成网络和 HTTPS 检查，再开启监控。
3. 管理员点击“添加微信接收人”，插件显示服务器生成的二维码。用接收人的手机微信扫码、确认；如果微信要求数字配对码，在插件填写手机显示的数字。
4. 登录凭证由服务器调用官方账户存储函数保存，插件只获得短期二维码和状态，不获得微信登录 token。二维码过期或取消后需要重新发起；扫码期间不要公开分享二维码。
5. 绑定完成后管理员备注用户、分配关键词和间隔。新接收人不会自动订阅已有关键词，手机接收人不能修改监控配置。
6. 接收人给 ClawBot 发一条消息后，管理员检查会话是否可用，再按需要发送测试消息。测试推送会发送真实微信消息，不应作为无提示的自动安装步骤。

确认目标时，查看插件“运行位置”中的“远端采集 · 本机不访问 Mercari”、已连接的 HTTPS 地址及服务运行状态。连接阶段还会检查版本和远端 HTTP 采集标识。地址应与自己的服务器域名一致；若误填本机地址或其他服务，先纠正连接设置。日常修改关键词和开始／暂停不需要修改源码，只有服务器部署配置、域名或插件 ID 变化时才需要调整对应配置。

第一次在新服务器部署只含源码，不包含原电脑的微信登录和配置，通常需要在服务器重新扫码并设置关键词。不要让本机和服务器同时轮询同一套复制的微信凭证；本项目不自动迁移已有本机绑定。初次采集只建立上一轮基线，不直接推送已有商品。

## 更新和重启

关键词、屏蔽词、间隔和开始/暂停通过 API 即时生效，不需要重启进程。更新服务端代码则需要重启。

建议先下载新代码到单独目录并运行测试，确认通过后进入短暂维护窗口：停止服务、切换代码或拉取已审查版本、启动服务并检查健康状态。若只使用一个 Git 工作目录，可以在停止服务之后更新，避免运行中的进程读到新旧混合代码：

```sh
sudo systemctl stop mercari-watch
cd /opt/mercari-watch/current
git pull --ff-only
sudo systemctl start mercari-watch
sudo systemctl status mercari-watch --no-pager
```

服务收到 SIGTERM 后停止新的调度并保存状态、关闭监听和微信轮询。systemd 模板预留 120 秒退出窗口；异常强制终止可能中断在途网络请求。运行数据使用独立目录，正常重启不会要求重新建立首轮基线，也不会清空微信队列，但微信自身登录失效仍需重新扫码。先备份数据再进行任何存储格式或上游插件升级；备份包含私密凭证，应与数据目录同等保护。

若新版本启动失败，停止服务并恢复上一代码版本后再启动，保留数据目录。跨存储版本回滚前检查迁移兼容性，不要只回退代码就假定兼容。仅更新插件界面、服务端接口未改变时，无需重启服务。

## 上线验收

- 本机可通过 HTTPS 连接服务，错误密钥被拒绝；外部不能直接访问 Node 明文端口。
- 先只用一个关键词和较长间隔，验证日本服务器能直接取得足量非广告个人商品及 Shops 商品。存在验证码、页面变更、访问限制或无法确认广告时应显示失败，保留旧基线，不推送不完整结果。
- 首次仅建基线，第二轮只有新出现的商品码才推送；屏蔽词按已保存规则过滤。
- 暂停全部任务后观察没有新增 Mercari 请求，管理 API 仍能响应；恢复后按设置检查。
- 每位微信接收人使用独立队列，一人断开不会阻塞其他人；新用户未分配关键词时不会收到上新。
- 重启后配置、上一轮结果和待发队列保留；确认没有因为重启将已有列表当作新商品。

目前尚未提供实际服务器地址、SSH 或域名，因此此轮交付范围是代码、配置模板及部署文档；这些线上验收由实际部署后完成。

本轮本地验证（2026-10-20）：124 项自动化测试、桌面／移动面板检查和实际微信官方 SDK 的空服务启动通过；没有进行真实扫码或微信发送。单次 Mercari 匿名直连探测返回 `MERCARI_NETWORK / UND_ERR_CONNECT_TIMEOUT`，尚未收到 HTTP 响应，不能据此判断日本服务器的可用性。协议按官方网页脚本核对，商品响应测试使用明确标注的模拟数据；真实商品字段、个人与 Shops 混排及广告排除仍需用上述探测命令在目标服务器验收。

## 微信接口接受，但手机没有显示

`accepted`、队列中的 `doneAt` 和面板“接口已接收”只表示发送调用没有报告失败，不表示手机已经显示或用户已读。上游消息编号也不是手机送达回执。不能仅凭返回 `ret: 0` 或待发数量为 0 就排除客户端漏收。

后续更新会为新发送请求保留经过白名单过滤的回执：客户端消息编号、接受时间、`ret`、`errcode`，以及返回的数字 `message_id`（若有）。不保存完整原始响应、账号令牌或会话令牌。缺失／格式异常的消息编号单独记录，保持原有发送完成与重试语义；不会因缺少可选编号而自动重发。

在服务器上查询最近 3 条记录：

```sh
cd /opt/mercari-watch/current
sudo /opt/node-v24.22.0-linux-x64/bin/node tools/inspect-wechat-delivery.mjs --limit 3
```

也可以按商品或发现消息编号定位，选项可重复：

```sh
sudo /opt/node-v24.22.0-linux-x64/bin/node tools/inspect-wechat-delivery.mjs --product-id m79154429293
sudo /opt/node-v24.22.0-linux-x64/bin/node tools/inspect-wechat-delivery.mjs --message-id new-333ac0d7-19fb-469e-931f-c2fb67ae7386
```

工具只读取监控与队列文件，不访问网络、不读取登录凭证、不发送消息、不改变队列。`receiptRecord: not-recorded` 表示没有保存回执，不能倒推出当时微信没有返回编号；旧版已完成消息无法补回原始响应。按商品查询依赖保留的最近发现记录，记录滚动移除后需要用消息编号定位。合并发送的原始发现会关联到实际合并请求的回执。

若需要新的可控样本，由接收人在微信发一条消息刷新会话，再由管理员在插件点击一次“测试微信”，核对手机实际显示，并运行上述诊断。不要仅凭“接口接受”就认定送达，也不要自动重发所有已接受记录。此更新用于保存进一步取证所需的信息，尚不能宣称修复任何特定的上游漏收原因。
